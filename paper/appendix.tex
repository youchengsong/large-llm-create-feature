\subsection{Domain Knowledge and Verification Statistics}
\label{sec:appendix_knowledge}


This appendix illustrates the five knowledge types for the SimECNY AML dataset ($\sim$200K digital yuan transactions). One example per type is shown; similar structured knowledge is compiled for all types (38 indicators, 15 rules, 12 expert opinions, 309 court documents).

\smallskip
\noindent\textbf{Schema Metadata.}
Column names, data types, and basic statistics extracted from the transaction data. Example fields include \texttt{amount} (numeric), \texttt{wallet\_type} (categorical, 4 types: anonymous, personal, enterprise, merchant), \texttt{hour} (numeric, 0--23), \texttt{src}/\texttt{dst} (wallet identifiers), and \texttt{transaction\_mode} (8 categories).

\smallskip
\noindent\textbf{Risk Indicator} [IND\_05]:
Dimension: transaction behavior anomaly. Field: single-day transaction count. Accounts exceeding regulatory daily thresholds indicate potential money mule activity. Each indicator includes a risk dimension, relevant data field, and expected directionality.

\smallskip
\noindent\textbf{Detection Rule} [RULE\_006]:
\emph{Scatter-in, gather-out.} Logic: daily incoming count $\geq$ 20 AND daily amount $\geq$ 1{,}000{,}000, with high incoming but low outgoing count. Python hint: group by \texttt{(src, date)}, filter accounts with many small inflows and few large outflows. Each rule includes a confidence level and a Python implementation hint for the agent.

\smallskip
\noindent\textbf{Expert Opinion} [EXP]:
Online ``running-score'' laundering: anonymous wallet $\to$ real-name wallet $\to$ bank account chain transfers after midnight. Amounts 300--5{,}000 yuan, sustained 10--30 days, daily volume at wallet limits.

\smallskip
\noindent\textbf{Court Document Evidence} [CASE]:
Criminal judgment on concealing proceeds. Pattern: digital yuan wallets across 6 banks creating a multi-layer fund channeling network via intermediary wallets and corporate-to-personal conversion.

\smallskip
\noindent\textbf{Verification Statistics.}
On SimECNY, KnowFeat generates 52 candidates across 4 rounds: 47 pass L1 (90\%), 31 pass L2 (60\%), and 18 pass L3 (35\%), with progressive filtering saving $\sim$53 minutes by avoiding unnecessary L3 evaluations on the 21 candidates rejected at L1/L2. When the optional post-hoc selection pass is enabled for the holdout experiment, 4 features are retained in the final model (as reported in Section~\ref{subsec:rq2}). The gap between 18 L3-accepted and 4 final features illustrates the importance of evaluating redundancy in combination rather than relying on individual gains alone.

\subsection{Practical Considerations}
\label{sec:practical}

We discuss practical aspects of deploying KnowFeat based on our experience with the SimECNY dataset.

\textbf{Compliance Integration.}
Provenance cards map directly to existing AML compliance review processes. The knowledge asset identifiers (e.g., RULE\_006, IND\_15) reference the same regulatory documents that compliance officers work with. Domain experts from the Postal Savings Bank of China reported that the structured format reduced feature review time from 2--3 hours to 15--30 minutes per feature, as the reasoning chain eliminates the need to reconstruct the designer's rationale. This aligns with regulatory requirements that mandate documenting the basis for suspicious transaction reporting.

\textbf{Lessons Learned.}
Three insights emerged: (1)~\emph{Knowledge curation cost varies by domain}: the full AML knowledge base (38 indicators, 15 rules, 12 expert opinions, 309 court documents) required $\sim$1 person-week, dominated by court document review which was semi-automated via an LLM-based key-clue extractor. In contrast, the simplified knowledge bases for public datasets (10--14 indicators, 8--10 rules, 6--8 expert consensus items per dataset) were constructed in 30--60 minutes each with LLM assistance, extracting domain facts from authoritative guidelines and documentation. This suggests that knowledge curation is practical for well-documented domains.
(2)~\emph{Verification thresholds require domain calibration}: the L3 acceptance criteria (e.g., $\Delta$Recall $> 0$ with Precision $\geq 90\%$) must be set with domain stakeholders. (3)~\emph{Feature maintenance is ongoing}: regulatory requirements evolve, and a periodic refresh cycle (e.g., quarterly) would be necessary in production.

% \textbf{Adaptability to New Domains.}
% KnowFeat's design is domain-agnostic: the five knowledge types serve as a general template that can be instantiated for a wide range of tabular classification tasks. Our public dataset experiments demonstrate this adaptability---we constructed knowledge bases for healthcare (diabetes, heart, breast\_w, blood\_transfusion), finance (credit\_g), marketing (bank\_marketing), and census (adult) domains using publicly available guidelines and documentation. The key requirement is that a domain expert can articulate risk indicators, detection rules, and expert heuristics in structured natural language; the LLM agent handles translation to executable code. The verification pipeline (L1/L2) is fully domain-agnostic; only the L3 acceptance metric and threshold require domain calibration (as noted above), and the semantic dimension decomposition can be adapted to any feature space (e.g., clinical vs.\ demographic features in healthcare). Knowledge curation is straightforward for well-documented domains; for others, the schema-only mode provides a starting point with knowledge incrementally added over time.
