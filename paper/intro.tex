\section{Introduction}
\label{sec:intro}

Feature engineering is widely recognized as one of the most impactful steps in building machine learning models for tabular data~\cite{domingos2012few}. Well-crafted features can dramatically improve model accuracy, reduce overfitting, and provide interpretable signals for downstream tasks. However, manual feature engineering is labor-intensive, requires deep domain expertise, and does not scale across diverse applications.

To address this challenge, automated feature engineering (AutoFE) methods have been developed. Traditional AutoFE approaches such as OpenFE~\cite{zhang2024openfe} and AutoFeat~\cite{horn2020set} apply systematic transformations---mathematical operations, aggregations, and feature crosses---to existing columns, then select the most predictive ones. While effective, these methods are purely data-driven: they explore a predefined transformation space without any understanding of what the features \emph{mean} or why certain transformations might be useful for a given domain.

The emergence of large language models (LLMs) has opened a new paradigm for feature engineering. Methods such as CAAFE~\cite{hollmann2024llmsgeneratefinanciallyrelevantfeatures} and FeatLLM~\cite{han2024featllm} use LLMs to generate feature transformation code based on dataset descriptions. These approaches leverage the LLM's broad world knowledge to propose semantically meaningful features---for example, generating a ``debt-to-income ratio'' for a credit dataset without being explicitly told to do so. However, current LLM-based methods suffer from three fundamental limitations:

\textbf{(1) No structured domain knowledge.}
Existing methods rely entirely on the LLM's parametric knowledge, which is general-purpose and may be outdated, incomplete, or irrelevant to specialized domains. In high-stakes applications such as finance and healthcare, the relevant knowledge---risk indicators, detection rules, and expert judgment---exists in structured external sources that LLMs cannot access through their training data alone.

\textbf{(2) Weak or absent verification.}
CAAFE evaluates candidates with a simple logistic regression inside the generation loop, while FeatLLM performs no model-based validation at all. Neither method checks whether generated code executes correctly, whether features exhibit meaningful statistical properties, or whether they genuinely improve the target model's performance. This leads to the acceptance of noisy, redundant, or even harmful features.

\textbf{(3) No traceability.}
In regulated industries such as finance, healthcare, and legal compliance, model features must be auditable. Decision-makers need to understand \emph{why} a feature was created and \emph{what evidence} supports its relevance. Existing methods output code snippets without any provenance information, making them unsuitable for deployment in environments that require explainability and accountability.

In this paper, we propose \textbf{KnowFeat} (\textbf{Know}ledge-guided \textbf{Feat}ure engineering), a framework that addresses all three limitations. KnowFeat has three core components:

\begin{itemize}
    \item \textbf{Hierarchical Knowledge Injection.} We organize domain knowledge into five levels of increasing specificity: (i) schema-only metadata, (ii) risk indicators, (iii) detection rules, (iv) expert opinions, and (v) evidence extracted from court documents. This hierarchy is \emph{ablatable}: we can systematically study the contribution of each knowledge level. The LLM agent receives the relevant knowledge as structured context and is instructed to ground every generated feature in specific knowledge assets.

    \item \textbf{Three-Stage Verification Pipeline.} Each candidate feature passes through three verification stages. \emph{L1 (Execution)}: the generated code is executed in a sandbox to ensure correctness. \emph{L2 (Statistical Quality)}: the feature is checked for information value (IV), Kolmogorov--Smirnov (KS) statistic, redundancy with existing features, and missing rate. An automatically calibrated noise threshold (from 100 random features at the 95th percentile) prevents low-quality features from proceeding. \emph{L3 (Model Effectiveness)}: the feature is evaluated with XGBoost on the actual target metric (delta-AUC) across 5 random seeds, ensuring that only features with a genuine positive contribution are accepted.

    \item \textbf{Intelligent Search Strategy.} We decompose the feature space into semantic dimensions and allocate a per-round budget to each. After each round, SHAP analysis identifies which dimensions have contributed least, and the budget is reallocated inversely---directing the agent to explore underrepresented areas. A failure memory prevents the regeneration of previously rejected features, while a forward selection mechanism discovers feature combinations that are individually weak but collectively strong.
\end{itemize}

We evaluate KnowFeat on seven public tabular datasets from OpenML, covering finance, healthcare, and marketing domains. Our experiments compare KnowFeat against five baselines: No-FE (no feature engineering), OpenFE, AutoFeat, CAAFE, and FeatLLM. Key findings include:

\begin{itemize}
    \item KnowFeat achieves the highest AUC on 4 out of 7 datasets (credit\_g, blood\_transfusion, breast\_w, adult) and ranks in the top two on 6 out of 7, while generating 3--10$\times$ fewer features than FeatLLM.
    \item Ablation experiments demonstrate that domain knowledge is essential: the schema-only variant generates zero accepted features on the diabetes dataset, while the full knowledge hierarchy consistently outperforms schema-only on 5 of 6 remaining datasets.
    \item Every generated feature includes a provenance card linking it to specific knowledge assets (e.g., RULE\_001, IND\_05), providing full auditability.
\end{itemize}
