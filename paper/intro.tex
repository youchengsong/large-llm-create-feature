\section{Introduction}
\label{sec:intro}

Feature engineering is among the most impactful steps in building machine learning models for tabular data~\cite{domingos2012few}. Well-designed features improve model accuracy, reduce overfitting, and provide interpretable signals for downstream tasks. However, manual feature engineering requires deep domain expertise and does not scale across diverse applications.

Traditional automated feature engineering (AutoFE) methods such as OpenFE~\cite{zhang2023openfe} and AutoFeat~\cite{horn2019autofeat} apply systematic transformations (mathematical operations, aggregations, and feature crosses) to existing columns, then select the most predictive ones. These methods are purely data-driven: they explore a predefined transformation space without understanding what the features \emph{mean} or why certain transformations might be useful. In practice, understanding the \emph{semantic} meaning of features is crucial in regulated domains such as finance and healthcare, where stakeholders must know \emph{what} a feature represents before deploying it.

The emergence of large language models (LLMs) has opened a new paradigm for feature engineering. Methods such as CAAFE~\cite{hollmann2023caafe}, FeatLLM~\cite{han2024featllm}, and LLM-FE~\cite{abhyankar2025llmfe} use LLMs to generate feature transformation code from dataset descriptions, leveraging the LLM's broad world knowledge to propose semantically meaningful features. However, current LLM-based methods share three limitations:

\textbf{(1) Lack of hierarchical, structured domain knowledge.}
Most methods rely on the LLM's parametric knowledge, which may be outdated or incomplete for specialized domains. None organizes external domain knowledge (regulatory indicators, detection rules, expert opinions, and case evidence) into a hierarchical format for systematic injection.

\textbf{(2) Insufficient verification.}
Existing verification mechanisms remain incomplete. CAAFE uses a logistic regression proxy; LLM-FE uses downstream accuracy without statistical filtering; FeatLLM performs no model-based validation. No method combines code execution, statistical quality filtering, and full model evaluation in a unified pipeline.

\textbf{(3) Limited explainability.}
In regulated industries, model features must be explainable. Decision-makers need to understand \emph{why} a feature was created and \emph{what evidence} supports it. Existing methods lack structured provenance that traces each feature to specific knowledge assets with detailed reasoning chains.

We propose \textbf{KnowFeat} (\textbf{Know}ledge-guided \textbf{Feat}ure engineering), a framework that addresses all three limitations:

\begin{itemize}
    \item \textbf{Hierarchical Knowledge Injection.} We organize domain knowledge into five types of increasing specificity (schema metadata, risk indicators, detection rules, expert opinions, and court document evidence) and inject them as structured context into the LLM agent.

    \item \textbf{Three-Stage Verification Pipeline.} Each candidate passes through L1 (code execution sandbox), L2 (statistical quality with noise-calibrated thresholds), and L3 (model effectiveness via XGBoost across 5 seeds).

    \item \textbf{Explainable Provenance.} Every accepted feature carries a structured provenance card recording the knowledge assets, reasoning chain, computation steps, and verification results.
\end{itemize}

We evaluate KnowFeat on seven public tabular datasets from OpenML and a realistic anti-money laundering (AML) dataset, synthesized to match production digital currency transaction patterns, containing 200{,}000 transactions with 93 baseline features. Key findings:

\begin{itemize}
    \item On public datasets, KnowFeat achieves the best average rank (1.4) among eight methods with 12--46 features per dataset, compared to 98--1{,}124 for FeatLLM.
    \item On the AML dataset, 18 knowledge-guided features improve Recall by +2.1pp and F1 by +1.5pp over the 93-feature baseline, outperforming all baselines.
    \item Ablation experiments confirm that domain knowledge is essential: the schema-only variant generates zero accepted features on one dataset, and the full hierarchy outperforms schema-only on 5 of 6 remaining datasets.
\end{itemize}

Section~\ref{sec:experiments} describes our experimental setup, results, and representative feature analysis. Section~\ref{sec:conclusion} concludes with limitations and future directions.
