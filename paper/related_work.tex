\section{Related Work}
\label{sec:related}

\subsection{Traditional Automated Feature Engineering}

Automated feature engineering aims to reduce the manual effort of creating predictive features from raw data. Early approaches focus on exhaustive transformation search: Nargesian et al.~\cite{nargesian2017learning} propose learning-based feature engineering for classification, Deep Feature Synthesis~\cite{kanter2015deep} recursively applies aggregation and transformation primitives along relational paths, while ExploreKit~\cite{katz2016explorekit} enumerates unary, binary, and higher-order operators over existing features and uses meta-learning to rank candidates. AutoFeat~\cite{horn2019autofeat} constructs features through polynomial and interaction terms, then applies L1 regularization for selection. More recently, OpenFE~\cite{zhang2023openfe} frames feature generation as an operator-operand search problem, using a two-stage expansion-and-selection pipeline with LightGBM-based feature importance to achieve state-of-the-art performance on tabular benchmarks.

These methods share a common limitation: they operate in a \emph{syntactic} transformation space, applying predefined mathematical operators without any semantic understanding of the data domain. For example, computing \texttt{age $\times$ income} is treated identically to \texttt{age $\times$ zip\_code}, even though only the former has financial meaning. This leads to a combinatorial explosion of candidates, most of which are semantically meaningless, and an inability to generate domain-specific features that require conceptual understanding---for instance, ``transaction velocity'' or ``dormant account reactivation'' in the context of transaction anomaly detection.

\subsection{LLM-Based Feature Engineering}

The emergence of large language models~\cite{brown2020gpt3,touvron2023llama} has enabled a paradigm shift from syntactic to semantic feature generation. CAAFE~\cite{hollmann2023caafe} iteratively prompts an LLM with dataset descriptions and evaluation feedback to generate Python code for new features, using logistic regression as a proxy evaluator. FeatLLM~\cite{han2024featllm} takes a two-pass approach: first extracting natural language rules from the LLM, then converting these rules into binary indicator features. LLM-FE~\cite{abhyankar2025llmfe} frames feature engineering as an evolutionary optimization problem, using LLMs to iteratively generate and refine features through structured prompts with model performance feedback. In the financial domain, RiskTagger~\cite{li2025risktagger} uses an LLM agent with regulatory knowledge to annotate Web3 crypto laundering behaviors, demonstrating that domain knowledge can enhance LLM-based data annotation.

These methods vary in their use of domain knowledge and verification. LLM-FE and RiskTagger incorporate limited domain context (dataset descriptions and regulatory guidelines, respectively), but none organizes knowledge into a hierarchical, structured format for systematic injection. Verification also varies: CAAFE uses a weak proxy model, LLM-FE uses downstream model accuracy, and FeatLLM performs no model-based validation. None combines code execution, statistical quality filtering, and model evaluation into a unified pipeline. Furthermore, while RiskTagger provides natural language rationales, none offers structured provenance that traces each feature to specific knowledge assets.

Tool-augmented LLM agents~\cite{yao2023react} have been applied to code generation~\cite{qian2024chatdev}, data analysis~\cite{hong2024data}, and scientific discovery~\cite{boiko2023autonomous}. In data science, AIDE~\cite{jiang2025aide} and DS-Agent~\cite{guo2024ds} automate end-to-end pipelines but do not address knowledge-grounded feature generation. KnowFeat builds on the tool-use paradigm by equipping an LLM agent with specialized tools for data exploration, feature generation with provenance, and multi-stage verification.

Table~\ref{tab:comparison} summarizes the key differences. KnowFeat is the first method to combine hierarchical structured domain knowledge, multi-stage verification (L1--L3), and full feature provenance tracking within an LLM-based feature engineering framework.

\subsection{Domain Knowledge Integration in Machine Learning}

The integration of domain knowledge into machine learning has a long history. Knowledge-infused learning~\cite{kursuncu2020knowledge} incorporates external knowledge graphs into neural architectures. In the feature engineering context, domain experts traditionally encode their knowledge as hand-crafted features---a process that is effective but does not scale. Transfer learning approaches~\cite{weiss2016survey} implicitly transfer knowledge through pretrained representations, but these are primarily designed for unstructured data (text, images) rather than tabular features.

In the financial domain specifically, AML feature engineering relies on expert-defined indicators such as transaction velocity, structuring patterns, and network centrality measures~\cite{chen2018aml}. Recent work has also explored graph-based approaches for financial forensics~\cite{weber2019anti}. Regulatory bodies publish typologies and red-flag indicators (e.g., FATF guidelines~\cite{fatf2012recommendations}), and financial institutions maintain internal detection rules derived from compliance experience and legal proceedings. This rich, structured knowledge has not been systematically leveraged by automated feature engineering methods.
